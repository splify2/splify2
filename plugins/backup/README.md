# backup — архив настроек

Официальный плагин splify2 (`splify2-core-plugins`): выгрузка настроек роутера в файл и восстановление из него. Служит
образцом: он пользуется платформой **только через её API**
([splify2-api](https://github.com/splify2/plugin-sdk/blob/main/docs/splify2-api.md)); `s2p lint --official` и стенд
`tests/pluginhygiene.sh` отказывают плагину, который заглянет в файлы, переменные или функции каркаса.

## Что делает

Плагин знает **формат архива** и умеет передавать его по кускам. Всё остальное берёт у платформы:

| Что едет в архив | Кто знает, что это и как проверять |
|---|---|
| спека, подписки, выбор у групп, ключи туннелей xsteer, поля uci каркаса | хост: `splify2-host state export\|check\|import` |
| свои списки, настройки других плагинов | сами плагины: хук `backup_sections` (операции `export`, `check`, `restore`) |

Методы на объекте `splify2` прежние: `backup_get`, `backup_put` (в плагине — `get` и `put`). Права `write`, а не `read`: в
архиве приватные ключи туннелей и ссылки узлов.

## Какие точки API использует

| Точка API | Где |
|---|---|
| Манифест: `compat`, `i18n`, `rpc`, `splify2` (псевдонимы, схема настроек) | `plugin.json` |
| **Методы rpc** и псевдонимы старых имён | `bin/backup`, `lib/archive.sh` |
| **Службы хоста**: `state check\|export\|import` (настройки каркаса), `hook backup_sections` (разделы плагинов) | `$SPLIFY2_HOST` |
| **Схема настроек** и значение через API (`s2_setting max_archive_kb`) | `settings.schema.json` |
| **Словари** `i18n`: `plugin.name`, `plugin.description` (RU, EN), строки схемы (`i18n/core/ru.json`) | `i18n/` |
| Рабочий каталог `STEER_PLUGIN_STATE` (память, закрытый 0700): сюда собирается и принимается архив | `lib/archive.sh` |

Хуков, задач и событий у плагина нет: архив собирается и восстанавливается по запросу человека, ничего не делая по
расписанию и ни на что не подписываясь. Слот интерфейса не нужен: карточка архива — часть каркаса.

## Формат

Строчный, с разделами в квадратных скобках; содержимое дословное. Заголовок `splify2-backup N`, комментарии, разделы:
`[spec]`, `[sub]`, `[sub имя]`, `[select]`, `[xsteer имя]`, `[plugin <id> <имя>]`, `[options]`. Версия формата — по набору
разделов: 3 — разделы каркаса, 4 — плюс разделы плагинов (строки раздела плагина едут с отступом в один пробел). Разбор
принимает любую версию не новее своей; более новую отвергает целиком.

Архивы формата 3 (до выноса каталога списков в плагин) восстанавливаются: `[list …]` и поля `manifest_url`,
`list_shrink_factor` из `[options]` переезжают к плагину `lists-catalog` его разделами.

## Порядок восстановления

1. Присланный файл разбирается строгим разборщиком по разделам (недоверенный ввод: размер, управляющие байты, имена).
2. **Проверка всего, ничего не записывая:** настройки каркаса — `state check`, данные плагинов — операция `check`.
3. Запись: сначала разделы плагинов (`restore`) — спека из архива ссылается на файлы, которые они кладут, — затем настройки
   каркаса (`state import`: подписки и ключи раньше спеки, спека проверяется ядром).
4. Применения нет: восстановленное человек видит как неприменённое и применяет сам.

## Настройки

| Ключ | Что |
|---|---|
| `max_archive_kb` | предел размера архива (КБ): он собирается и принимается в памяти; больший архив отклоняется с названием размера |

## Проверка

```sh
sh tests/rpcdmatch.sh       # разбор присланного файла, отказы, круг выгрузка → восстановление
sh tests/hostmatch.sh       # службы хоста, на которых стоит плагин
sh tests/pluginhygiene.sh   # граница API
sh /путь/к/plugin-sdk/tests/compat/run.sh plugins/backup
```
